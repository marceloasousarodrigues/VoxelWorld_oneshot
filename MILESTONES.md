# M6 — Player & World Navigation

## Objective

Introduce a controllable first-person player into the existing rendered voxel world.

The milestone must connect player input and basic player movement to the voxel terrain established in M5.

The existing M1–M5 systems remain the foundation for the player and navigation system.

## Requirements

### 1. First-Person Player

Implement a player entity suitable for first-person voxel-world navigation.

The player must have a defined world position and camera.

### 2. Player Spawn

Spawn the player at a valid position within or above the generated world.

The player must not start inside solid terrain.

### 3. First-Person Camera

Provide a first-person camera attached to the player.

The camera must follow the player's position.

### 4. Keyboard Movement

Implement basic first-person movement:

- forward;
- backward;
- left;
- right.

Movement must use the existing world coordinate system.

### 5. Mouse Look

Implement first-person mouse-look camera control.

Horizontal and vertical camera rotation must be supported.

### 6. Gravity

Implement basic gravity for the player.

The player must fall when not supported by terrain.

### 7. Ground Detection

Detect when the player is standing on terrain.

The player must not continuously fall through the world.

### 8. Basic Terrain Collision

Implement basic collision between the player and solid voxel terrain.

The player must not move through solid terrain.

Collision must use the existing Chunk/block data rather than introducing an unrelated representation of the world.

### 9. Jumping

Implement a basic jump action while the player is grounded.

The player must not be able to repeatedly jump while airborne.

### 10. Existing World Integration

The player must navigate the world generated by the M5 pipeline.

M6 must reuse:

- M1 coordinate system;
- M2 Chunk block data;
- M3 Chunk mesh generation;
- M4 World container;
- M5 terrain generation;
- M5 rendered Chunk Entities.

### 11. Runtime Validation

The application must be executed and directly validated.

Validation must demonstrate:

- player spawning;
- first-person camera;
- keyboard movement;
- mouse look;
- gravity;
- ground detection;
- jumping;
- collision with terrain.

Source-code inspection alone is insufficient for movement and collision requirements.

### 12. Previous Milestone Compatibility

M6 must not break the functionality established by M1, M2, M3, M4, or M5.

The existing voxel terrain must remain rendered and usable as the navigation environment.

## Out of Scope

The following are explicitly outside M6:

- block breaking;
- block placement;
- block selection;
- block highlighting;
- textures;
- advanced lighting;
- inventory;
- crafting;
- items;
- mobs;
- NPCs;
- water;
- biomes;
- world streaming;
- Chunk loading/unloading;
- persistence;
- multiplayer;
- advanced physics;
- vehicles;
- combat;
- health/damage;
- animations;
- LOD;
- greedy meshing;
- unrelated refactoring.

## Validation

The following requirements require direct runtime validation:

- player spawning;
- first-person camera;
- keyboard movement;
- mouse look;
- gravity;
- ground detection;
- jumping;
- terrain collision.

Source-code inspection alone is insufficient to prove these runtime requirements.

The application must be executed and the player must be directly tested inside the generated voxel world.

## Completion

M6 is complete only when all mandatory requirements above are satisfied.

Runtime behavior must be directly validated.

M6 must preserve the functionality established by M1, M2, M3, M4, and M5.

M7 must not be started automatically.

The next milestone becomes active only when explicitly selected by the user or parent task.


# M7 — Block Interaction

## Objective

Introduce basic runtime interaction with the voxel world by allowing the player to select, break, and place blocks.

M7 must build on the player, camera, terrain, Chunk, World, mesh, and texture systems established in M1–M6.

The milestone must make the voxel world interactive without introducing inventory, crafting, items, or other gameplay systems.

## Requirements

### 1. Block Raycast

Implement a raycast from the first-person camera into the voxel world.

The raycast must:

- originate from the player's camera/view;
- detect the first solid voxel intersected by the ray;
- use the existing World/Chunk block data;
- have a defined maximum interaction range;
- ignore empty/air space.

The interaction range should be approximately 6 blocks unless a different value is required by the existing implementation.

### 2. Block Selection

The player must be able to identify the block currently targeted by the raycast.

The selected block must provide:

- world block coordinates;
- block type;
- the face hit by the raycast.

The selection must update as the player looks around.

### 3. Block Highlighting

Visually highlight the currently selected block.

The highlight must:

- clearly identify the selected voxel;
- follow the selected block as the camera moves;
- disappear when no valid block is within interaction range;
- not modify the underlying block data.

A simple wireframe/outline representation is sufficient.

### 4. Block Breaking

Implement block breaking using the primary mouse button.

When the player activates the break action:

- the selected block must be removed;
- the block must become `BlockType.AIR`;
- the affected chunk must be marked for mesh regeneration;
- the rendered chunk must update to reflect the change.

The player must not be able to break an invalid/air block.

### 5. Block Placement

Implement block placement using the secondary mouse button.

When the player activates the placement action:

- place a block on the face adjacent to the selected block;
- use one of the existing block types;
- update the underlying World/Chunk data;
- regenerate the affected chunk mesh;
- preserve the existing block textures.

The initial implementation does not require an inventory.

A fixed/default block type may be used for placement.

### 6. Player Placement Safety

The system must prevent placing a block inside the player.

Before placement, validate that the new block does not intersect the player's current body/collision volume.

If placement would overlap the player, the action must be rejected.

### 7. Chunk Boundary Updates

Block interaction must correctly handle blocks at chunk boundaries.

When a block is changed:

- the containing chunk must be regenerated;
- if the changed block is on a chunk boundary, the relevant neighboring chunk(s) must also be regenerated when their visible geometry is affected.

No stale faces should remain visible at chunk boundaries after breaking or placing a block.

### 8. Existing World Integration

M7 must reuse the systems established by previous milestones:

- M1 coordinate system;
- M2 Chunk block data;
- M3 Chunk mesh generation;
- M4 World container;
- M5 terrain generation;
- M5 rendered Chunk Entities;
- M6 player;
- M6 first-person camera;
- M6 player collision and navigation;
- M6 world interaction position.

No unrelated replacement world/block representation should be introduced.

### 9. Texture Integration

Block interaction must preserve the existing block visual system.

Existing block types must continue to use their assigned visual representation:

- GRASS;
- DIRT;
- STONE.

Breaking and placing blocks must regenerate meshes without losing the block textures/UVs.

### 10. Runtime Validation

The application must be executed and directly validated.

Validation must demonstrate:

- raycast detection;
- block selection;
- block highlighting;
- breaking a block;
- placing a block;
- collision with newly placed blocks;
- correct texture rendering after changes;
- correct behavior at chunk boundaries;
- rejection of placement inside the player.

Source-code inspection alone is insufficient for the interaction and mesh-update requirements.

### 11. Previous Milestone Compatibility

M7 must not break the functionality established by M1–M6.

The following must continue to work:

- terrain generation;
- chunk rendering;
- block textures;
- first-person camera;
- WASD movement;
- mouse look;
- gravity;
- ground detection;
- jumping;
- terrain collision.
