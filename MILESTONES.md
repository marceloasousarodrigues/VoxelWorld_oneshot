# M7 — Block Interaction

## Objective

Introduce basic runtime interaction with the voxel world by allowing the player to select, break, and place blocks.

M7 must build on the player, camera, terrain, Chunk, World, mesh, and texture systems established in M1–M6.

The milestone must make the voxel world interactive without introducing inventory, crafting, items, or other gameplay systems.

## Requirements

### 1. Block Raycast

Implement a raycast from the first-person camera into the voxel world.

The raycast must:

- originate from the player's camera/view;
- detect the first solid voxel intersected by the ray;
- use the existing World/Chunk block data;
- have a defined maximum interaction range;
- ignore empty/air space.

The interaction range should be approximately 6 blocks unless a different value is required by the existing implementation.

### 2. Block Selection

The player must be able to identify the block currently targeted by the raycast.

The selected block must provide:

- world block coordinates;
- block type;
- the face hit by the raycast.

The selection must update as the player looks around.

### 3. Block Highlighting

Visually highlight the currently selected block.

The highlight must:

- clearly identify the selected voxel;
- follow the selected block as the camera moves;
- disappear when no valid block is within interaction range;
- not modify the underlying block data.

A simple wireframe/outline representation is sufficient.

### 4. Block Breaking

Implement block breaking using the primary mouse button.

When the player activates the break action:

- the selected block must be removed;
- the block must become `BlockType.AIR`;
- the affected chunk must be marked for mesh regeneration;
- the rendered chunk must update to reflect the change.

The player must not be able to break an invalid/air block.

### 5. Block Placement

Implement block placement using the secondary mouse button.

When the player activates the placement action:

- place a block on the face adjacent to the selected block;
- use one of the existing block types;
- update the underlying World/Chunk data;
- regenerate the affected chunk mesh;
- preserve the existing block textures.

The initial implementation does not require an inventory.

A fixed/default block type may be used for placement.

### 6. Player Placement Safety

The system must prevent placing a block inside the player.

Before placement, validate that the new block does not intersect the player's current body/collision volume.

If placement would overlap the player, the action must be rejected.

### 7. Chunk Boundary Updates

Block interaction must correctly handle blocks at chunk boundaries.

When a block is changed:

- the containing chunk must be regenerated;
- if the changed block is on a chunk boundary, the relevant neighboring chunk(s) must also be regenerated when their visible geometry is affected.

No stale faces should remain visible at chunk boundaries after breaking or placing a block.

### 8. Existing World Integration

M7 must reuse the systems established by previous milestones:

- M1 coordinate system;
- M2 Chunk block data;
- M3 Chunk mesh generation;
- M4 World container;
- M5 terrain generation;
- M5 rendered Chunk Entities;
- M6 player;
- M6 first-person camera;
- M6 player collision and navigation;
- M6 world interaction position.

No unrelated replacement world/block representation should be introduced.

### 9. Texture Integration

Block interaction must preserve the existing block visual system.

Existing block types must continue to use their assigned visual representation:

- GRASS;
- DIRT;
- STONE.

Breaking and placing blocks must regenerate meshes without losing the block textures/UVs.

### 10. Runtime Validation

The application must be executed and directly validated.

Validation must demonstrate:

- raycast detection;
- block selection;
- block highlighting;
- breaking a block;
- placing a block;
- collision with newly placed blocks;
- correct texture rendering after changes;
- correct behavior at chunk boundaries;
- rejection of placement inside the player.

Source-code inspection alone is insufficient for the interaction and mesh-update requirements.

### 11. Previous Milestone Compatibility

M7 must not break the functionality established by M1–M6.

The following must continue to work:

- chunk rendering;
- block textures;
- first-person camera;
- WASD movement;

# M8 — Inventory, Hotbar & Resource Collection

## Objective

Introduce a basic inventory and resource collection system into the existing voxel world.

M8 must extend the block interaction mechanics established in M7 by allowing the player to collect resources, store block items, select blocks through a hotbar, and use collected resources for block placement.

The milestone must establish the foundation for future gameplay systems without introducing unrelated mechanics.

M8 must build on M1–M7 and preserve the existing world, Chunk, mesh, texture, player, and interaction architecture.

## Requirements

### 1. Inventory System

Implement a player inventory capable of storing block items.

The inventory must:

- Store item types and quantities.
- Support adding items.
- Support removing items.
- Track available quantities correctly.
- Reject invalid item types and invalid quantities.
- Prevent item quantities from becoming negative.
- Handle inventory capacity consistently.

The initial implementation may use a fixed number of inventory slots.

The inventory must be independent of the World and Chunk block-data representations.

### 2. Item Stacks

Implement stackable inventory items.

The system must:

- Allow multiple items of the same type to occupy one slot.
- Enforce a configurable maximum stack size.
- Merge compatible stacks when adding items.
- Use empty slots when an existing stack cannot accommodate the full quantity.
- Handle inventory-full conditions without silently losing items.
- Preserve item type and quantity consistency.

Stacking rules must be defined independently of visual rendering.

### 3. Hotbar

Implement a hotbar that allows the player to select an inventory slot.

The hotbar must:

- Expose a configurable number of quick-access slots.
- Support selection through keyboard input.
- Track the currently selected slot.
- Display the selected slot visually.
- Show the item type and quantity in each occupied slot.
- Handle empty slots correctly.
- Update immediately when inventory contents change.

The hotbar must provide the selected block type to the existing block-placement system.

### 4. Block Collection

Implement resource collection when the player breaks a block.

When a block is broken:

- The block must be removed using the existing M7 interaction system.
- The corresponding resource must be added to the player's inventory.
- The collected item type must correspond to the broken block type.
- Collection must respect inventory and stack limits.
- Resources must not be duplicated.
- Inventory updates must not modify unrelated world blocks.

The initial implementation may collect resources immediately without spawning physical item entities.

### 5. Inventory-Aware Block Placement

Integrate the hotbar and inventory with the existing M7 placement system.

When the player places a block:

- The selected hotbar item determines the block type.
- The inventory must contain the required item.
- A successful placement consumes the appropriate quantity.
- A rejected placement must not consume items.
- Placement safety, interaction range, and existing raycast behaviour must remain intact.
- Chunk mesh regeneration and texture preservation must continue to work.

The existing fixed/default DIRT placement behaviour may remain available as a fallback during development, but the completed system must use the selected item when inventory-based placement is active.

### 6. Item and Block Type Mapping

Define a consistent mapping between world block types and inventory item types.

The initial implementation must support the existing block types:

- GRASS;
- DIRT;
- STONE.

The mapping must not rely on visual textures or mesh data to identify an item.

World block IDs, inventory item IDs, and texture assignments must remain consistent with their respective systems.

### 7. Inventory Interface

Implement a basic inventory interface suitable for the current game.

The interface must:

- Display inventory slots.
- Display item quantities.
- Show the selected hotbar slot.
- Allow the player to open and close the inventory.
- Remain separate from world rendering and Chunk entities.
- Avoid creating UI entities for individual world voxels.
- Update when inventory contents or selected slots change.

A simple functional interface is sufficient. Advanced UI styling is outside the scope of this milestone.

### 8. Tools and Mining Behaviour

Introduce a basic tool system only if the inventory and block-item pipeline is stable.

The initial tool system may support:

- Tool item definitions.
- Tool-to-block compatibility.
- Configurable mining speed.
- Optional durability values.

Tools must integrate with the existing block-breaking action rather than replacing the raycast or world mutation systems.

Tool durability must not become negative, and rejected or unsuccessful mining actions must not consume durability incorrectly.

Advanced tool progression and enchantments are outside the scope of M8.

### 9. World and Chunk Integration

M8 must reuse the systems established by previous milestones:

- M1 coordinate system;
- M2 Chunk block data;
- M3 Chunk mesh generation;
- M4 World container;
- M5 terrain generation and rendered Chunk Entities;
- M6 player, camera, movement, and collision;
- M7 raycasting, block selection, breaking, placement, and mesh refresh.

Inventory and item management must not introduce an alternative representation of the world.

The existing architecture invariants must remain intact:

- One logical block-data structure per Chunk.
- One combined mesh per rendered Chunk.
- One Ursina Entity per rendered Chunk.
- No entity per voxel or per mesh face.

### 10. Runtime Validation

The application must be executed and directly validated.

Validation must demonstrate:

non-tiling with visible seams when repeated per block. The higher-resolution
local candidates that would produce a genuine improvement are external assets
(and still 16x16 in the present pack), so per M11 the milestone is stopped here
pending a user decision.

   rendered pixels cannot be inspected.

## Requirements

### 1. Grass and Small Vegetation
- Use lightweight decorative geometry (crossed textured planes), not solid cubes.
- Place vegetation only on suitable exposed ground (`GRASS` with `AIR` above).
- Decorations must not obstruct player movement or interfere with block
  interaction.

### 2. Trees
- Start with one oak-like tree: trunk plus leaf canopy.
- Define tree dimensions, canopy shape, placement rules and spacing.
- Prevent trees from spawning underwater, inside terrain, or in unsuitable
  locations.
- Define how trees interact with existing blocks and future block modifications.

### 3. Deterministic Generation
- The same world seed must produce the same vegetation positions and tree shapes.
- Generation order and chunk loading order must not change results.
- Trees crossing chunk boundaries must generate consistently, without
  duplication or missing parts.

### 4. Rendering and Performance
- Preserve one combined mesh and one Ursina Entity per rendered terrain chunk.
- Do not create an individual Ursina Entity for every grass tuft or leaf.
- Reuse existing textures and atlas infrastructure; identify any genuinely
  necessary new textures. (Result: none required; the local Minetest pack
  supplies the foliage, trunk and leaf sources.)

### 5. Testing
- Automated tests for deterministic placement, valid ground placement, tree
  structure, chunk boundaries, collisions, and regeneration.
- Runtime and visual verification defined separately from automated tests.
- Preserve all M1–M13 behavior, especially water simulation.

## Approved Design Decisions

1. Grass tufts are a per-`Chunk` decoration layer (logical metadata, like M13
   water metadata), not a `BlockType`, so they cannot interfere with movement,
   raycast, placement or water.
2. Trees are two new solid block types: `OAK_LOG = 6` and `OAK_LEAVES = 7`.
3. All foliage geometry is merged into the existing opaque chunk mesh; the
   opaque Entity receives an alpha-test (cutout) render state. The water child
   Entity is unchanged.
4. Generation is a pure function of `(seed, world coordinates)` using an explicit
   integer hash; no `random` module or builtin `hash()`.
5. Trees use a jittered `6`-block anchor grid with jitter `[2, 3]`, height `4..6`,
   canopy radius `2`, and a pure-function suitability test that prevents placement
   inside terrain or over water. `TREE_GRID = 6` with jitter `[2, 3]` is required,
   not merely default: it is the largest jitter that keeps every complete tree
   footprint (trunk included) inside its own grid cell, so footprints cannot
   overlap, while `CHUNK_SIZE = 16` is not a multiple of `6`, so trees really do
   cross X and Z chunk boundaries and can span a chunk corner. Ownership of a cell
   is the closed form `(cx // TREE_GRID, cz // TREE_GRID)`, so which tree writes a
   cell never depends on chunk-generation order.

## Out of Scope

- more than one tree type; biomes, flowers or crops;
- leaf decay, tree falling, sapling growth or regrowth;
- animated foliage;
- new item/tool/crafting gameplay;
- water changes, buckets or fluid–vegetation interaction;
- world streaming, dynamic chunk loading or persistence;
- renderer rewrite, per-block Entities, LOD or greedy meshing;
- changes to existing block IDs or existing texture assignments;
- repairing the truncated M13 documentation.

## Objective

Diagnose the reported stuttering when breaking blocks rapidly, and prepare an
evidence-based plan for performance and scalability as the world grows towards a
Minecraft-like size.

The cause must be identified by profiling and reproducible benchmarks before any
optimisation is proposed. The plan must distinguish confirmed bottlenecks from
hypotheses that still require measurement.

## Requirements

### 1. Reproducible Baseline

Establish a reproducible baseline before changing anything, covering single and rapid
block breaking, chunk-boundary edits, rapid placement, dirty-chunk updates, water
under increasing activity, chunk generation and loading, traversal while generating
chunks, rendering with increasing visible chunk counts, and worlds containing grass,
trees and active water.

Measure frame-time percentiles (p50/p95/p99/max), the counts of frames exceeding
16.67 ms and 33.33 ms, CPU attribution across interaction, world updates, mesh
generation, water and chunk generation, mesh rebuild counts and durations, chunk
loaded/active/visible/unloaded counts, pending work queues, memory over time, and FPS
as a secondary metric only.

### 2. Evidence Before Optimisation

Any proposed optimisation must cite measurements. Optimisations that do not
demonstrate an improvement must be reverted and reported as "measured, no benefit".

### 3. Architecture Preservation

The logical Chunk remains the authoritative source of block data. One combined terrain
mesh and one Ursina Entity per rendered Chunk is preserved. The existing chunk, mesh,
interaction, collision and world-generation contracts are preserved. No entity per
block is introduced. Splitting a chunk into multiple rendered entities is not proposed
unless measurements demonstrate the current design is inadequate and the trade-off is
explicitly approved.

### 4. Water Preservation

M13 water behaviour, determinism and update contracts are preserved. Simulation
correctness must not be weakened to improve frame rate.

### 5. Previous Milestone Compatibility

M15 must not break M1–M14 functionality, particularly block interaction, chunk-boundary
updates, natural generation and water behaviour. Existing tests must not be modified or
weakened.

### 6. Measurable Acceptance Criteria

The milestone must define measurable acceptance criteria for interaction-related frame
time, controlled frame time under rapid block changes, bounded pending work, bounded
memory growth within the intended active-world model, correct chunk loading,
unloading, regeneration and boundary behaviour, and absence of M1–M14 regressions.
Numerical targets must be established from the recorded baseline rather than invented.

### 7. Instrumentation Separation

Diagnostic profiling must be separated from instrumentation that remains in the final
game, and from normal gameplay measurements.

### 8. Approval Gate

Implementation must not begin until the plan has been reviewed and explicitly approved,
including the decisions listed in the design specification.

## Out of Scope

The following are explicitly outside M15 until explicitly approved:

- dynamic chunk streaming, unloading or view-distance implementation;
- changes to chunk dimensions or the one-entity-per-chunk model;
- changes to M13 water semantics;
- changes to M14 generation rules, textures or atlas assets;
- greedy meshing;
- LOD;
- multithreading, multiprocessing or compute shaders;
- renderer replacement;
- unrelated refactoring of M1–M14.

**What changed.**

- `chunk.py` - `Chunk.apply_water_cells(...)`: batch form of `set_water_level` /
  `clear_water`; writes the block grid, levels and sources for many cells in one
  vectorised step and returns the occupancy-change mask.
- `world.py` - `World.apply_water_batch(chunk_key, cells)`: batch form of `set_water`
  with identical rules (never creates a chunk, never enters the external-edit log, never
  invalidates its own job, skips `world_y < 0`) and the same dirty/neighbour
  invalidation, computed once per touched chunk face instead of once per cell.
- `water.py` - the job pipeline is now `flood -> solve -> prepare -> commit -> done`.
  `prepare` groups the solved region into one write batch per chunk under the tick
  budget; `commit` applies those batches under the tick budget. Both resume across ticks
  and the batch order is the sorted chunk key. `is_finished()` is now reachable.
- `main.py` - comment only: a committing tick marks chunks dirty and lets the frame
  loop's bounded `reconcile()` publish the geometry, so the mesh budget and the water
  budget are never spent in the same tick.

**Consistency strategy, and the trade-off it makes.** Publication is atomic *per chunk*:
all of a chunk's cells are applied in one vectorised write, so a chunk is never
observable with its block grid and its water metadata disagreeing, and that chunk's mesh
is only rebuilt after the chunk is complete. Atomic publication of the *whole region* and
bounded per-frame work cannot both hold in this architecture, so the region is published
chunk by chunk across a small number of frames; that is observable through
`WaterSimulation.has_pending_work()`, which stays true until every batch is applied.
`tests/test_m15_water_commit.py` asserts that no chunk was ever seen in a non-final state
at the moment its batch landed, and that no chunk was ever applied twice.

## M16 — Chunk Streaming & World Management

### Goal

Implement dynamic chunk loading and unloading around the player to support exploration of larger worlds while controlling CPU usage, rendering workload, and memory consumption.

The system must integrate with the existing `World`, `Chunk`, terrain generation, water simulation, mesh generation, and player systems without breaking established architecture invariants.

### Scope

- **Chunk streaming**
  - Track the player's current chunk coordinates.
  - Determine which chunks should be loaded based on a configurable horizontal render/streaming distance.
  - Load required chunks as the player moves through the world.
  - Unload chunks that fall outside the configured retention distance.
  - Avoid unnecessary work when the player remains within the same chunk.

- **World management**
  - Keep the logical world registry authoritative.
  - Prevent duplicate chunks and duplicate rendered entities.
  - Separate logical chunk existence from rendered chunk entity lifecycle where necessary.
  - Preserve existing world-coordinate conversion and negative-coordinate behavior.
  - Ensure chunk creation, registration, removal, and lookup remain consistent.

- **Generation and rendering integration**
  - Reuse the existing terrain generation and mesh generation pipelines.
  - Avoid generating or rebuilding chunks that are already valid.
  - Process streaming work incrementally to prevent large synchronous operations during player movement.
  - Prioritize chunks near the player over distant chunks.
  - Correctly handle chunk boundaries and neighboring chunk dependencies.

- **State preservation**
  - Define explicitly which chunk state is persistent and which state can be regenerated.
  - Ensure unloading does not silently lose player modifications or other authoritative world state.
  - Preserve water simulation correctness when chunks enter or leave the active world.
  - Ensure pending generation, mesh, or water work cannot publish stale results for unloaded or replaced chunks.

- **Configuration**
  - Centralize streaming distance and per-frame work limits in the existing configuration system.
  - Avoid hard-coded streaming settings throughout the implementation.

### Architecture invariants

1. The logical `Chunk` remains authoritative for its block data and world state.
2. Each rendered chunk has at most one corresponding Ursina entity.
3. A chunk must not be registered or generated twice for the same coordinates.
4. Chunk-local and world-coordinate calculations must work correctly for negative coordinates.
5. Loading and unloading must not leave stale entities, mesh references, or invalid world-registry entries.
6. Existing player interactions, terrain generation, vegetation, and water behavior must remain correct.
7. Streaming work must make incremental progress and eventually converge to the desired loaded-chunk set.

### Tests

- Deterministic tests for the desired loaded-chunk set at different player positions.
- Movement across positive and negative chunk boundaries.
- No duplicate chunks or rendered entities during repeated movement.
- Correct loading and unloading at the streaming-distance boundary.
- Unloaded chunks are removed from the appropriate registries and have their rendered resources released.
- Re-entering an unloaded area restores the correct terrain and preserves authoritative modifications.
- Neighboring chunks remain correct when loaded or unloaded.
- Pending work for unloaded chunks cannot create stale entities or overwrite newer state.
- Water sources, propagation, and pending simulation work behave correctly across chunk lifecycle changes.
- Streaming work respects configured per-frame limits, with tests proving progress and eventual completion.
- Regression tests for existing chunk, mesh, player, vegetation, and water behavior.

### Runtime verification

- Move the player across multiple chunk boundaries in both directions.
- Verify that chunks load ahead of the player and distant chunks unload.
- Verify correct behavior at negative coordinates and world boundaries.
- Confirm that rendered entity count remains consistent with the active loaded set.
- Confirm that revisiting an area restores the expected world state.
- Check for visible gaps, stale meshes, duplicate entities, or interaction failures.
- Measure frame-time spikes and memory behavior during sustained exploration.

### Non-goals

- Multiplayer or networked chunk streaming.
- Procedural terrain redesign.
- Changes to the established block or water simulation rules unless required for lifecycle correctness.
- Persistent world save/load files unless explicitly added to the approved design.
- Unrelated rendering, texture, inventory, or gameplay features.

### Acceptance criteria

- [x] Chunk loading and unloading operate correctly as the player moves.
- [x] The active chunk set follows the configured streaming and retention distances.
- [x] No duplicate chunks, entities, or stale rendered resources remain after repeated transitions.
- [x] Existing terrain, player modifications, and water state follow the documented persistence policy.

- [x] Per-frame streaming work is bounded by the implemented scheduling policy, with any unavoidable unbounded operations explicitly documented.
- [x] All new tests and the complete existing test suite pass.
- [x] Runtime exploration confirms correct behavior across positive and negative chunk boundaries.
- [x] CPU, frame-time, and memory measurements are recorded, with GPU and visual limitations clearly identified.
- [x] Architecture and milestone documentation are updated to reflect the implemented behavior.

### Dependencies

- M1–M6: Coordinate utilities, block data, mesh generation, world management, terrain generation, and player/collision.
- M7: Block interaction and dirty-chunk refresh.
- M10–M12: Texture configuration and asset pipeline.

### Design summary

- `World` owns lifecycle; `ChunkStreamer` owns policy. Streaming is horizontal

  and persist in the overlay; water spread is derived and re-solves from sources.
- Load **and** unload bump `water_edit_version`, so a water job built on the old
  domain is discarded and re-queued rather than publishing stale results.
- `ChunkStreamer.rendered` is a complete rendered registry: it adopts chunks that
  entered the world outside the streamer (the initial region), so one entity per
  loaded chunk is provable at any time.

### Diagnosis (measurement-only phase)

Full report: `docs/superpowers/specs/2026-10-12-m16-gameplay-stutter-diagnosis.md`.

4. **`BlockHighlight` churn:** 2.203 ms median per create/remove event, rebuilding 13

## M40 v3 - Block Placement Preview and Orientation Feedback

**Status: COMPLETE**, with the documented limitations below. This record adds the
placement-usability fix to the completed M40 work.

**Base:** `5da7cbb`. **Code commit:** `68a8d8e`
(`M40: add block placement preview and orientation feedback`). **Canonical
project:** `C:/Users/Admin/Documents/Projects/VoxelWorld_Godot`.

**Reported defect and root cause.** Placement was only explained by a HUD line;
the player could not see the destination cell, the block's actual partial shape,
or its rotated state before committing the action. `VoxelPlayer.place_selected()`
and the HUD's `placement_preview()` also implemented the same rules twice, so a
visual preview built independently would have been able to drift from the real
placement transaction.

**Implemented.**
- `VoxelPlayer.placement_preview()` is now the single authority for destination
  cell, orientation, validity, refusal message and preview visibility.
  `place_selected()` consumes that exact dictionary, so ghost and placement
  cannot disagree.
- `BlockPlacementPreview` builds its geometry with the real `ChunkMesher` from a
  one-cell isolated chunk using the previewed block id and orientation. Cubes,
  stairs, slate stairs, slabs, ramps, ridges, stations and other custom models
  therefore use their real shapes rather than a separate approximation.
- The ghost shows the destination cell outline and real geometry in green when
  valid and red when invalid. Invalid occupancy is drawn through the occupying
  block so the refusal cannot be mistaken for a valid cell.
- The targeted surface has its own amber face patch; the destination cell is a
  separate outline/ghost. This distinguishes the surface the crosshair hit from
  the cell that will be filled.
- Slabs show their actual lower or upper half geometry. The HUD names the exact
  state (`bottom half` / `top half (upside down)`), derived from the existing
  targeted-face rule.
- Directional pieces reuse the existing `placement_facing` / `R` rotation path.
  A 3D arrow and a cyan forward-face marker show stair/ramp facing; a cyan strip
  along the long axis shows ridge orientation. The final placement consumes the
  same orientation value the ghost displays.
- The ghost hides when no placeable item is selected, an interface owns input,
  the game is not playing, there is no target, or the destination is outside the
  buildable height or an unloaded chunk. Occupied and player-overlapping cells
  remain visible in the red invalid state.
- `--placement-capture=cube|slab|slab_top|stair|invalid` is a capture-only
  diagnostic that stages a flat pad and a real aimed cell; it does not add a
  second placement path.
- The ghost is visual only: no collision shape, no physics body, no world edit,
  no chunk write and no raycast participation. Its mesher is private so preview
  rebuilds do not pollute streaming performance counters.

**Verified.**
- Unit `M17_TESTS_PASS 3283 assertions` (baseline 3092; 191 new placement
  assertions).
- Integration `M17_INTEGRATION_PASS 519 assertions` (baseline 503; 16 new checks
  including real-raycast ghost visibility, inventory hiding, input gating and
  exact cell/orientation match after placement).
- Regression `M17_REGRESSION_PASS assertions=52`.
- Unit coverage includes cube placement on top and against all four side faces,
  lower and upper slab geometry, all eight stair orientations, all four ramp
  orientations, both ridge axes, occupied/inside-player/out-of-range/unloaded
  refusal, non-placeable item hiding and changing the selected block.
- Every unit geometry check reads the mesh built by the real chunk mesher; the

## M41c - First-Person Hand and Tool Visual Polish

**Status: COMPLETE**, with the documented limitations below.

**Canonical project:** `C:/Users/Admin/Documents/Projects/VoxelWorld_Godot`.

**Objective.** Raise the visual quality of the first-person hand and held tools
to the established world standard without changing camera, player, inventory,
aiming, mining or placement behaviour.

**Root cause found during implementation.** The M41b detail layers were modelled
on the item's negative-Z side, while the first-person camera sees the item's
positive-Z side. The lighter face plates, central boss, rivets, axe/shovel faces
and edge highlights were therefore hidden behind dark body shells. The wooden
tier also used almost the same brown for head and handle, the pick head was only
0.70 model units wide and 0.08 units thick, and the fist was built in arm space
with vertical finger strips instead of closing around the haft.

**Implemented.**
- Rebuilt the tool geometry with a consistent three-layer metal language: dark
  faceted body, lighter inset face and bright cutting edge, plus a lighter top
  bevel on both pickaxe arms. All visible layers and rivets are now on the
  camera-facing side.
- Pickaxe: broad 0.984-unit double head, heavy central eye with a domed ring boss
  and four corner rivets, layered faces, bright tips, shoulder bolsters, socket
  and leather binding.
- Axe: tall bearded blade with a flared top horn, concave lower beard, inset
  cheek, bright curved edge, poll face, eye bands, top lug, rivets and binding.
- Shovel: shaped spade with a rolled bright lip, recessed scoop face, raised
  spine, side edges, step, socket and rivets.
- Sword: layered blade with face, ridge and two edge strips, brass collar and
  guard, quillon studs, gem, pommel boss and leather grip.
- Every long tool has a four-section tapered haft, raised grain strips, a
  leather grip sleeve with five wraps, two metal collars, a riveted butt cap, a
  head-side ferrule and a second leather binding. All tiers now read as forged
  metal heads on warm wooden hafts.
- Rebuilt the fist in the held item's local frame: palm behind the haft, four
  horizontal finger wraps, side knuckles, dark creases, a three-part thumb and a
  wrist strap. The arm was moved right/up so the grip remains visible beside the
  hotbar; the sleeve was muted. The grip origin is inside the palm.
- Added per-item first-person holds and a higher grip on long hafts so the
  enlarged heads stay in the lower-right quadrant and clear of the reticle.
  Third-person rotations and scales were left unchanged.
- Added `test_tool_visuals.gd` (layered construction, material count, grip
  containment, per-tool screen bounds, reticle and swing clearance),
  `run_m41c_demo.gd` (eleven runtime frames) and `run_tool_preview.gd`
  (supplementary model inspection).
